### 1. Unit test failures (3)

All three failures are in *live* multi-model decision-gate comparators that
read pre-generated snapshots from `/tmp/decision_gate_<model>.json` and assert
that at least one snapshot exists. Without those fixtures pre-staged by a live
Gemini run, the assertions fire as `expected 0 to be greater than 0` instead of
the spec being skipped.

  1. [tests/decision_gate.multi.live.test.ts:147](apps/ui/tests/decision_gate.multi.live.test.ts:147)
     "decision-gate (multi-model) compares validator output across Gemini variants and writes a markdown table"
  2. [tests/decision_gate.real.live.test.ts:152](apps/ui/tests/decision_gate.real.live.test.ts:152)
     "decision-gate (multi-model, real track) compares validator output across Gemini variants on Vtss-CantCatchMe.mp3"
  3. [tests/decision_gate.stems.live.test.ts:168](apps/ui/tests/decision_gate.stems.live.test.ts:168)
     "decision-gate (multi-model, stem-aware, real track) compares per-model validator output with stemAnalysis populated"

Each test computes `const ok = gates.filter((g) => g.ok)` from `existsSync()`
checks against `/tmp/decision_gate_*.json`, then runs
`expect(ok.length).toBeGreaterThan(0)` unconditionally.

**Suspected cause:** the live test files were added without a corresponding
`describe.skipIf(noSnapshotsPresent, …)` (or similar guard) around the suite,
so they always fail in CI / fresh checkouts where the snapshots have not been
generated. The sibling [tests/decision_gate.live.test.ts](apps/ui/tests/decision_gate.live.test.ts) does
include skip handling.

**Suggested next step:** wrap each `it(...)` body in an early-return when no
snapshots exist (e.g. `if (gates.every((g) => !g.ok)) { test.skip(); return; }`)
or move these three files out of the default `vitest run` glob into a
separate live config. Do **not** delete the assertions — they are useful when
snapshots *are* present.

### 4. Needs human review (1)

[apps/ui/src/services/mixDoctor.ts:102](apps/ui/src/services/mixDoctor.ts:102) — `estimatePlr()`

```ts
function estimatePlr(phase1: Phase1Result): number | null {
  const explicit = asFiniteNumber(phase1.plr);
  if (explicit !== null) return roundTo(explicit, 2);
  const lufs = asFiniteNumber(phase1.lufsIntegrated);
  const truePeak = asFiniteNumber(phase1.truePeak);
  if (lufs === null || truePeak === null) return null;
  return roundTo(truePeak - lufs, 2);
}
```

Computes `truePeak − lufsIntegrated` as a *fallback* PLR when `phase1.plr` is
absent. This is technically a re-computation of a value that appears in the
Phase 1 schema (`plr`), but:

  1. It does not override `phase1.plr` when that field is present (early
     return on line 104).
  2. The result is consumed locally for advisory scoring; it is never written
     back into the Phase 1 snapshot.
  3. It mirrors the formal PLR definition (Peak − Integrated LUFS), so the
     fallback should not diverge from what Phase 1 would emit.

Listing here rather than auto-classifying because the rule "do not re-compute
a value that already exists in the Phase 1 output schema" admits two readings,
and the safer-but-stricter reading would still flag this.

**Suggested next step:** decide whether `estimatePlr` should instead surface
`{ plr: null, reason: 'phase1.plr missing' }` and ask the backend to always
emit `plr`, or keep the fallback and document it as an intentional derived
display rather than a Phase 1 override.

**Resolution (post-merge follow-up):** keep the fallback, document why.
Verified `analyze_plr` in [apps/backend/analyze_core.py:624-635](../apps/backend/analyze_core.py) computes
`round(true_peak − lufs_integrated, 2)` — byte-identical to the UI fallback —
and that `plr` is emitted in both `--fast` ([analyze.py:1385](../apps/backend/analyze.py))
and full ([analyze.py:1775](../apps/backend/analyze.py)) paths. The fallback fires only
when `phase1.plr` is null/undefined (legacy snapshots replayed from runtime
SQLite that predate the field) and lands on the same number the backend would
have. Documented inline above `estimatePlr` so the next audit doesn't re-flag
this. See [apps/ui/src/services/mixDoctor.ts:102](../apps/ui/src/services/mixDoctor.ts).
